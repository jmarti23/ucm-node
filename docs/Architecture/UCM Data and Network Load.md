# UCM Data and Network Load

**Status:** Current System Specification  
**Hardware Platform:** Waveshare ESP32-P4-WIFI6-POE-ETH  
**Environmental Sensor:** Sensirion SEN54  
**Network Protocol:** MQTT over IP  
**Hub:** UCM-HUB  
**Last Updated:** August 2026

---

## 1. Purpose

This document describes the data generated and transmitted by a UCM environmental sensor node and the resulting network load on the UCM system.

The purpose is to provide the UCM team with a clear understanding of:

- What information a node transmits
- How MQTT topics are organized
- How frequently data are transmitted
- The approximate data volume generated by a node
- How node traffic reaches UCM-HUB
- How the system can scale as additional nodes are deployed

The figures in this document describe the **current UCM implementation**. They should be updated when message frequency, payload structure, or network architecture changes.

---

# 2. UCM Data Architecture

UCM uses MQTT as the primary messaging protocol between environmental sensor nodes and the UCM Hub.

The basic architecture is:

```text
SEN54
  │
  ▼
ESP32-P4 UCM Node
  │
  │ MQTT
  ▼
UCM-HUB
  │
  ├── Mosquitto
  │
  ├── Telegraf
  │      │
  │      ▼
  │   InfluxDB
  │
  └── Other UCM services
```

The sensor node does not communicate directly with the database.

Instead, the node publishes MQTT messages to the UCM Hub.

The Hub acts as the central message broker and provides the point through which sensor data can be distributed to other UCM services.

---

# 3. Network Connectivity

A UCM node currently supports two network paths:

```text
Ethernet
   OR
Wi-Fi
```

The current network manager attempts Ethernet first.

If Ethernet is unavailable, the node uses its Wi-Fi configuration.

Once network connectivity is established, the node connects to the MQTT broker running on:

```text
UCM-HUB.local
```

The node therefore does not need to know the IP address of the Hub.

This allows the Hub's network address to change without requiring the firmware to be rebuilt with a new IP address.

---

# 4. MQTT Topic Architecture

UCM uses a node-specific MQTT namespace.

The basic structure is:

```text
ucm/node-<NODE_ID>/<MESSAGE_TYPE>
```

For example:

```text
ucm/node-UCM-E0A6EC/environment
ucm/node-UCM-E0A6EC/heartbeat
ucm/node-UCM-E0A6EC/info
ucm/node-UCM-E0A6EC/command
```

The node ID is therefore part of the MQTT topic.

This provides a simple mechanism for routing messages to a specific node.

---

# 5. Node Identity

Each node has a unique UCM node identifier.

For example:

```text
UCM-E0A6EC
```

The identifier appears in both the MQTT topic and the JSON payload.

Example:

```text
ucm/node-UCM-E0A6EC/environment
```

with a payload containing:

```json
{
  "node": "UCM-E0A6EC"
}
```

This redundancy is intentional.

The topic identifies the routing destination, while the payload identifies the originating node.

---

# 6. Environmental Data

The SEN54 provides the environmental measurements used by UCM.

The current UCM environmental payload contains:

```text
PM1.0
PM2.5
PM4.0
PM10
Temperature
Relative Humidity
VOC Index
NOx Index
```

A representative environmental message is:

```json
{
  "node": "UCM-E0A6EC",
  "timestamp": "2026-08-10T12:05:52Z",
  "pm1": 5.8,
  "pm25": 6.1,
  "pm4": 6.1,
  "pm10": 6.1,
  "temperature": 32.2,
  "humidity": 37.2,
  "voc": 0.0
}
```

The exact fields included in the current firmware should be treated as the authoritative implementation.

Future sensor firmware may add fields such as NOx when available.

---

# 7. Environmental Data Frequency

The current firmware is operating the SEN54 measurement cycle approximately once per second.

The serial output demonstrates the current behavior:

```text
SEN54 measurement
        │
        ▼
JSON environmental message
        │
        ▼
MQTT publication
```

Therefore, for purposes of current system-load analysis, the environmental stream should be treated as approximately:

**1 environmental message per second per node**

unless the firmware configuration is changed.

That corresponds to approximately:

```text
60 messages/minute
3,600 messages/hour
86,400 messages/day
```

per node.

---

# 8. Heartbeat Data

The node also publishes a heartbeat message.

A representative heartbeat is:

```json
{
  "node": "UCM-E0A6EC",
  "timestamp": "2026-08-10T12:05:52Z",
  "uptime_s": 32,
  "free_heap": 457000,
  "rssi": -29
}
```

The heartbeat provides operational information rather than environmental observations.

Current fields include:

- Node ID
- Timestamp
- Uptime
- Free heap
- Wi-Fi RSSI

The heartbeat is currently being published approximately once per second.

Therefore, each node currently produces approximately:

```text
86,400 heartbeat messages/day
```

---

# 9. Node Information

The node publishes an information message describing its identity and location.

Example:

```json
{
  "node": "UCM-E0A6EC",
  "name": "JC Office",
  "description": "Downtown Jersey City",
  "lat": 40.71780,
  "lon": -74.04310
}
```

The information message contains relatively static metadata.

It is not part of the continuous environmental data stream.

The information message is useful for:

- Node registration
- Mapping
- Human-readable identification
- Geographic visualization
- Node configuration

---

# 10. Command Data

The Hub can send commands to an individual node using the node-specific command topic.

For example:

```text
ucm/node-UCM-E0A6EC/command
```

An OTA command is currently:

```json
{
  "command": "ota"
}
```

The important architectural feature is that the node ID is part of the topic.

For example:

```text
ucm/node-UCM-E0A6EC/command
```

means:

> Send this command to node UCM-E0A6EC.

The MQTT broker does not need a separate routing mechanism.

The node subscribes specifically to its own command topic:

```text
ucm/node-UCM-E0A6EC/command
```

This is why the command issued from UCM-HUB can directly reference the node:

```bash
mosquitto_pub \
  -h UCM-HUB.local \
  -t 'ucm/node-UCM-E0A6EC/command' \
  -m '{"command":"ota"}'
```

This is a consequence of the UCM MQTT topic architecture and the node-specific subscription implemented by the firmware.

---

# 11. Current Message Classes

The current UCM MQTT architecture can therefore be summarized as:

| Topic | Direction | Purpose | Frequency |
|---|---|---|---|
| `/environment` | Node → Hub | Environmental measurements | ~1/sec |
| `/heartbeat` | Node → Hub | Node health/status | ~1/sec |
| `/info` | Node → Hub | Node identity/location | Infrequent |
| `/command` | Hub → Node | Node-specific commands | Event-driven |

The environmental and heartbeat topics create the continuous network load.

The info and command topics contribute comparatively little traffic.

---

# 12. Messages Per Node

Under the current approximately one-second environmental and heartbeat intervals:

```text
Environmental:
86,400 messages/day

Heartbeat:
86,400 messages/day

Total recurring:
172,800 messages/day/node
```

Therefore:

```text
~2 MQTT messages/sec/node
```

are generated by the two recurring streams.

This is the current implementation and should not be interpreted as the final production telemetry rate.

---

# 13. Network Traffic Versus Message Count

Message count alone does not determine network load.

Each MQTT message contains:

```text
MQTT protocol overhead
+
Topic
+
JSON payload
```

and is transported through the underlying network protocols.

The complete network transmission also includes protocol overhead associated with:

```text
MQTT
TCP
IP
Ethernet or Wi-Fi
```

Therefore, the actual number of bytes transmitted is larger than the JSON payload alone.

For this reason, UCM should track both:

```text
Messages per second
```

and:

```text
Bytes per second
```

when evaluating network capacity.

---

# 14. Approximate Payload Size

The JSON payloads generated by the current firmware are relatively small.

For example, an environmental message contains a node identifier, timestamp, and sensor measurements.

A heartbeat contains:

```text
Node ID
Timestamp
Uptime
Free heap
RSSI
```

The exact byte count depends on the serialized JSON representation.

For engineering purposes, the actual MQTT traffic should eventually be measured from the broker or captured at the network interface rather than estimated solely from the JSON strings.

---

# 15. Scaling the Network

Because each node has its own MQTT namespace, additional nodes add independent message streams.

For `N` nodes:

```text
Environmental messages/day:

86,400 × N
```

and:

```text
Heartbeat messages/day:

86,400 × N
```

Therefore:

```text
Total recurring MQTT messages/day:

172,800 × N
```

Examples:

| Nodes | Messages/day |
|---:|---:|
| 1 | 172,800 |
| 10 | 1,728,000 |
| 25 | 4,320,000 |
| 50 | 8,640,000 |
| 100 | 17,280,000 |

These figures assume the current approximately one-message-per-second rates for both environmental data and heartbeat traffic.

---

# 16. Data Volume

Message count should not be confused with database storage.

The system has several stages:

```text
Sensor
  │
  ▼
JSON
  │
  ▼
MQTT
  │
  ▼
Telegraf
  │
  ▼
InfluxDB
```

MQTT traffic includes protocol overhead that does not necessarily become stored data.

InfluxDB also stores measurements using its own data representation, including timestamps, fields, and tags.

Consequently, the number of bytes transmitted over the network is not equivalent to the number of bytes ultimately stored in InfluxDB.

A future UCM capacity study should therefore calculate:

1. Network traffic
2. MQTT broker load
3. Telegraf processing load
4. Database write rate
5. Database storage growth

separately.

---

# 17. Network Bandwidth

The current UCM traffic volume is expected to be small relative to the capacity of a conventional Ethernet or Wi-Fi network.

The more important scaling issue is likely to be **message processing and storage**, rather than raw network bandwidth.

At the current rate of approximately two recurring MQTT messages per second per node, even a substantially larger node population remains modest in terms of raw network throughput.

However, the system should be evaluated experimentally as the network grows.

The UCM-HUB also performs functions beyond MQTT transport, including:

- MQTT brokering
- Telegraf ingestion
- InfluxDB storage
- Web services
- GIS/dashboard services

Therefore, Hub capacity cannot be evaluated solely by available network bandwidth.

---

# 18. Telemetry Frequency and Future Optimization

The current one-second environmental and heartbeat intervals are useful during development because they provide high visibility into node behavior.

They may not represent the optimal production configuration.

Future deployments may use configurable intervals such as:

```text
Environmental telemetry:
configurable

Heartbeat:
configurable
```

Reducing telemetry frequency would reduce:

- MQTT message count
- Network traffic
- Broker workload
- Telegraf processing
- Database write frequency
- Database storage growth

However, telemetry frequency should remain a deliberate system-design decision rather than being changed solely to reduce traffic.

The current rates should therefore be considered the **baseline implementation**.

---

# 19. Data Integrity and Message Format

UCM uses JSON payloads for MQTT messages.

This provides several advantages:

- Human readability
- Easy debugging
- Simple integration with Python and web services
- Easy inspection with MQTT command-line tools
- Extensibility
- Straightforward ingestion into Telegraf

The node identity is included in both the MQTT topic and JSON payload.

Timestamps are represented in UTC using ISO 8601 formatting.

Example:

```text
2026-08-10T12:05:52Z
```

This provides a consistent temporal reference across geographically distributed nodes.

# 21. Hub-Centric Architecture

The current architecture intentionally places the MQTT broker on UCM-HUB.

Nodes publish to the Hub rather than directly to downstream databases or applications.

This provides several benefits:

- Centralized message management
- Simplified node firmware
- Separation of sensing from data storage
- Multiple downstream consumers
- Easier monitoring
- Easier network expansion
- Reduced coupling between nodes and applications

It also makes it possible to add additional processing systems without changing the sensor node.

---

# 22. Scaling Beyond One Hub

The UCM architecture anticipates the possibility of multiple hubs.

A larger deployment can be organized conceptually as:

```text
Node Group A
     │
     ▼
UCM-HUB-A
     │
     ├── MQTT
     ├── Telegraf
     ├── Database
     └── Local services

Node Group B
     │
     ▼
UCM-HUB-B
     │
     ├── MQTT
     ├── Telegraf
     ├── Database
     └── Local services
```

A higher-level research or aggregation system can consume data from multiple hubs if required.

This allows UCM to scale geographically or organizationally without requiring every node to communicate directly with a central server.

# 23. Current Data-Load Baseline

The current UCM implementation establishes the following baseline:

```text
Environmental telemetry:
~1 message/sec/node

Heartbeat:
~1 message/sec/node

Recurring MQTT traffic:
~2 messages/sec/node

Recurring messages:
~172,800/day/node
```

These values represent the current firmware behavior observed during development.

They should be treated as a **baseline for capacity planning**, not as an immutable production requirement.

# 24. Future Validation

As the UCM system develops, the following should be measured experimentally:

- Actual MQTT bytes/sec per node
- Actual bytes/day per node
- MQTT broker CPU utilization
- MQTT broker memory utilization
- Telegraf processing rate
- InfluxDB write rate
- InfluxDB storage growth
- Network utilization
- Hub capacity as node count increases

A controlled load test should eventually be performed using multiple simulated or physical nodes.

The purpose will be to determine the practical capacity of a UCM-HUB before additional hubs are introduced.

**Current status: OPERATIONAL BASELINE**

The current UCM system has a functioning MQTT data path from environmental sensor nodes through UCM-HUB and into the downstream data infrastructure.

The current message architecture is established.

The approximate message rates documented here are based on the current firmware behavior observed during development.

Exact byte-level network consumption and long-term storage requirements remain subjects for future measurement.

# 26. Summary

UCM uses MQTT and JSON to move environmental and operational data from distributed ESP32-P4 sensor nodes to UCM-HUB.

Each node has a unique MQTT namespace:

```text
ucm/node-<NODE_ID>/
```

The principal recurring data streams are:

```text
/environment
/heartbeat
```

with node metadata and commands handled through:

```text
/info
/command
```

At the current development configuration, each node generates approximately:

```text
1 environmental message/sec
+
1 heartbeat message/sec
=
~2 recurring MQTT messages/sec
```

or approximately:

```text
172,800 recurring messages/day/node
```

The current architecture is therefore capable of supporting distributed environmental sensing while keeping the sensor nodes relatively simple and placing aggregation, storage, and higher-level processing on UCM-HUB.

As the network expands, UCM should measure actual byte-level traffic and Hub processing/storage requirements rather than relying solely on message counts.
